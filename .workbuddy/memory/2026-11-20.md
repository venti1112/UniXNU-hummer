## 构建路径备忘

- 内核/payload 只能在 macOS 或 CI（macos-15）编；本机 CachyOS 只能跑 prepare。
- 仓库是 fork（venti1112/UniXNU-hummer ← 2426120557/UniXNU-hummer），fork 的 Actions 需手动启用。

  `-c commit.gpgsign=false`（需用户同意）。

  BootShim 入口的 x1 指向解压后镜像里的 FD，payload 就在 x1+PcdFdSize；
  SEC 把它塞进同一个 HOB（结构 {Dtb, Payload}）；RamDiskDxe 新增 `PublishPayload()`：
  校验 FAT32 引导扇区（0xAA55、`FAT32`、512B/sector）并从 BPB 的 total sectors 算长度，

## v220：根因是 512 对齐检查，payload 地址对 512 取余恒为 112

### 用工具复算出的确定事实
`boot-hummer-v219.img` 的 kernel 字段是 **gzip 流 + 尾部 DTB**（不是裸数据）。
`zlib.decompressobj(31)` 解压后 170,918,000 B，布局：

| 偏移 | 内容 |
|---|---|
| 0 | BootShim，`_Payload` 在 112 |
| 112 | FD（FVMAIN_COMPACT），0x300000 |
| 3,145,840 | payload FAT32 镜像，167,772,160 |

`3145840 % 512 = 112`。而 `PublishPayload` 里写着：

```c
if ((Address & 0x1FF) != 0) { Flags |= RDSK_FLAG_ADDR_ALIGN; return FALSE; }
```

于是 payload **每一次都在这里被拒**，然后掉进 `PublishInitrd` 分支。
这个检查本身是错的：`mRamBase` 只是个字节指针，所有读取都走 `ReadLogical()` 的
`CopyMem`，既没有 DMA 也没有对齐要求。删掉它即可。

### 顺带查清的两件事
- `PcdFdBaseAddress=0xA7100000`（`UEFI_FD` 段），`PcdFdSize=0x300000`；
  `PcdSystemMemorySize` 全仓无人赋值（默认 0），所以 `ArmPlatformPkg/MemoryInitPeiLib`
  那条路没走，实际用的是 `SiliciumPkg/Library/MemoryInitPeiLib/MemoryInitPei.c`，
  内存图完全来自 `hummerPkg/Library/MemoryMapLib` 的静态表。
- 表里 `Kernel` 段 = `0xA8000000 + 0x10000000`，`Reserv`。解压后的镜像正是落在这里，
  所以 payload 区间**本来就被预留**，不会被 DXE 复用。`ReservePayload` 的
  `AllocatePages` 反而会因为"已分配"而失败，`rv` 非 0 属正常，不是故障。

### v220 改动
1. `PublishPayload`：删掉 512 对齐早退，改为只置 `RDSK_FLAG_UNALIGNED` 后继续。
2. 驱动入口先写 `Signature='RDSK'` + `RDSK_FLAG_ENTRY`，用来区分"驱动没跑"与"跑了但失败"。
3. 底栏改为一行（`Ui.Info` 是单行居中绘制，不能塞 `\n`）：
   `rd%u v%u c%u s%u b%u %x/%x/%x p%x:%08x f%x g%x h%08x a%lx`
   - `g` = marker Signature（`4b534452` = 我们的驱动；`0` = 没跑/内存被清）
   - `f` = Flags，`2b` = ENTRY|PAYLOAD_OK|MAGIC_OK|UNALIGNED 全通
   - `h` = payload 前 4 字节（大端拼装，正常应为 `eb58904d`）
   - `a` = payload 基地址
