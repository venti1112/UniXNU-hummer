## v220 panic 定位：SMMU 规划把「我们自己的残留映射」当成冲突

### panic 屏逐字段解码（用户手工 OCR，红绿蓝三条线在顶部）
- `UFS ROOT FAILURE: conflicting UFS stream mapping`、`stage=SMMU planning result=e00002d8`
  （`e00002d8` = `kIOReturnNotReady`）
- `SMMU smr=80000060 s2cr=00000001 cbar=00000000 sctlr=00000000`
- `SMMU slot=1 id1=60000053`、`id2=5111`、`cba2r=0`
- `@NativeUfs.cpp:1340`

### 解码
- `id1=0x60000053` → `banks = 0x53 = 83`、`pages = 1<<(((id1>>28)&7)+1) = 128`
  → 最高 bank = 82，`(128+83)*4096 = 0xd3000`，必须靠 SM8750 的 `kUfsSmmuMapBytes=0x100000`
  才过几何检查（默认 `0xd0000` 会判 "unsupported SMMU geometry"）。这条反过来证明 id1 读数可信。
- `smr=0x80000060` → VALID + stream 0x60、mask=0；`s2cr=0x1` → TYPE=0、CBNDX=**1**。
- 规划器从 bank 82 往下找，`ourBank` 要求 `s2cr&255 == p.bank`，永远不等于 1
  → `usable=false` → `conflicting UFS stream mapping`，`slot=1` 与屏幕完全一致。
- **注意**：失败路径不写 `gRootDiagnostic.cbar/sctlr`，屏上那两个 0 是默认值，不是硬件读数。
  据此不能推断 bank 1 未被配置（PKX110 的 run-15 探针里对应的 bank 0 是 `SCTLR.M=1` + `CBAR=0x12345000`）。

### 根因
`SmmuTakeover.h: planUfsSmmuBank` 只允许两种「我们自己的条目」：已经落在我们选的 bank 上（reuse），
或者 `NATIVE_UFS_SM8750` 特判的 `s2cr == 0`（PKX110 固件把 SID 0x60 留在 bank 0）。
hummer 固件把 SID 0x60 留在 **bank 1**，`s2cr=1` 不在特判里 → 直接 panic。
上游注释只考虑了反方向（别的 stream 占了我的 bank），没考虑「我的 stream 已被映射到别的 bank」。

### 修法（`patches/native-ufs-sm8750.patch`，改 `SmmuTakeover.h` + `tests/SmmuTakeover.cpp`）
- 精确匹配（`mask == 0` 且只有一条）时，**不管它指向哪个 bank 都归我们处置**：
  `p.reuse = ourBank`，落在别处就由 `configureUfsSmmu` 把 S2CR/SMR 改写到选定 bank。
- 只有通配（`mask != 0`）或同一 stream 的第二条条目才算 `conflicting UFS stream mapping`。
- `retryable` 去掉 "conflicting"（它已与 bank 无关，重试 8 次纯浪费）。
- 保留「复用 bank 的 CBA2R/CBAR 不符预期就不修复」的守卫：不再原地修，而是下移一个 bank；
  测试里把下方 bank 全部占住以保持「拒绝时不写硬件」这条性质仍被覆盖。

## v221 上机：SMMU 修好了，卡在「分区名不存在」

### SMMU 修复确认生效
panic 屏从 `conflicting UFS stream mapping`（`s2cr=00000001`）变成：
- `s2cr=00000052` → **CBNDX=0x52=82**，正是规划器算出的 bank（`p.bank = banks-1-bankFromTop`）
- `cbar=00010000`、`cba2r=1` 也都写进去了（v220 那两个 0 是失败路径的默认值）
- 新 panic 是 `UFS ROOT FAILURE: no selected root partition`、`stage=GPT entries`

### 解码：GPT 完全读对了
- `stage=GPT entries` 只在 header 校验（magic/rev/CRC/geometry）全过之后才设置（RootLayout.h:103）
- `result=00000000` = `kIOReturnSuccess`（RootCommands.h:229，scsiStatus==0 时）
- `why` 落在 `no selected root partition` 而不是 `GPT entries CRC` → **entries CRC 通过**
- 所以 `partition=0..0`、`magic=00000000`、`manifest=4294967295` **全是 bzero 后的默认值**：
  `first/last` 只在找到分区后赋值（L149），`magic/manifest` 在 `!found` 早退路径根本不写
- 真正结论：**128 个条目里没有名为 `unixnu` 的分区**

### 根因
`UFS_ROOT_PARTITION` 在 `NATIVE_UFS_SM8750` 分支里是 `"unixnu"`，来自 PKX110/13T 移植。
hummer 出厂 GPT 没有这个条目。上游自己的注释（NativeUfs.cpp:1834）写的是
`LUN 0 GPT -> "userdata" -> its first block`，但那是**非** SM8750 分支的行为。
`native-ufs-root` 只是启用开关（`rootMode != 0`），分区名是编译期常量，改不了。

### 决策：建独立 unixnu 分区（用户选择，保留安卓）
不走「把 UFS_ROOT_PARTITION 改成 userdata 再覆盖 220 GiB userdata」那条路。
- `patches/native-ufs-sm8750.patch` 的 `UFS_ROOT_PARTITION` **保持 `"unixnu"`**
  （曾改成 userdata 提交 c248935，随后在 b84ab14 回退；blob 哈希回到 `05bd3bb`）
- `board.toml [userdata]` 加 `partition = "unixnu"`；`first_lba/last_lba` 仍是旧 userdata
  范围，**切完分区必须更新**，否则 `--dry-run` 的容量结论是错的
- userdata 实际容量：`0x3a1421..0x3ad07fa` = 220.74 GiB（256 GB 机型）
- 镜像大小：CI 日志里的 OS 4.9 GiB + SystemOS 3.1 GiB ≈ **8 GiB**

### 新工具 `scripts/make-hummer-root-partition.py`
- 默认只读：抓 GPT → 校验 header/entries CRC → 打印规划 → 存 `out/gpt-backup-*/`
- `--apply` 才写回，写前二次确认，写完读回比对，不一致自动用备份恢复
- **LBA 是 4096 字节**，所以 128 条 entry 只占 **4 个扇区**（不是 512B LBA 时的 32 个）；
  主 GPT 是 LBA 0..5。抓 34/33 个扇区只是留余量
- 走 `adb push` + `dd` 而不是管道（`adb exec-out` 只回传，`adb shell` 的 stdin 会做换行转换）
- 离线验证（造 GPT 往返）：32 GiB 切分后 `unixnu=53,282,811..61,671,418`、
  `userdata=3,806,241..53,282,810`（188.74 GiB）、`super` 未动、备份 GPT 落点

## recovery 环境特性（关键）

- `adb shell` 直接就是 `uid=0(root)`，**没有 `su` 二进制** —— 脚本的 `adb_su()` 必须
  先试 `adb exec-out id`，是 root 就直接执行，否则才 `su -c`
- 有 `dd` / `gzip` / `toybox`，`/dev/block/by-name/` 完整
- **`adb exec-out dd if=... 2>/dev/null` 是错误的**：`2>/dev/null` 被**本地** shell 吃掉，
  设备的 dd 进度文本（"N bytes copied, x M/s"）会混进 stdout，备份文件多出几十字节。
  正确写法是加引号让设备 shell 处理：`adb exec-out 'dd if=... 2>/dev/null' > file`
- recovery 里 userdata 是**加密**的，`dd` 只能拿到原始密文镜像，不可压缩；
  想拷文件必须回正常系统（解锁后）

## 第一次 --apply 失败：read-back mismatch（设备完好）

- 现象：`writing the primary GPT ... / writing the backup GPT ... / read-back mismatch!
  restoring the backup GPT ... / the write did not read back identically`
- **事后核对：主备 GPT 都与 `out/gpt-backup-20261121-173424/` 逐字节一致，
  sha256 仍是 `dc368597…` / `76036825…`，与 17:17 那份相同 —— 回滚成功，设备完好**
- 根因（三条叠在一起）：
  1. `dd` 带了 `2>/dev/null`，真实报错被吞，只剩笼统的 mismatch
  2. `dd` 写 `/dev/block/sda` 后没有 `fsync`，紧接着的回读可能命中缓存里的旧内容
  3. 主 GPT 写成功、备份写失败时不会回滚，会留下改了一半的状态
- 修复（commit 98903d0）：`conv=notrunc,fsync` + 写完 `sync` + 带回 stderr +
  统一 rollback 分支 + mismatch 时逐扇区打印 got/want 前 16 字节；
  `--restore` 也补了读回校验
- **两阶段重试法**（推荐）：
  1. `--restore <备份> --apply --yes` —— 写回**相同内容**，幂等，零风险；
     能 verify 过就说明写路径通了
  2. `--size-gib 64 --apply --yes` —— 真正切分
- 环境事实：`/dev/block/sda` = `brw------- root root`；`/data/local/tmp` 在
  rootfs（6.8 G ramdisk），push 139 KB 没问题；toybox dd 支持 `conv=notrunc,fsync`；
  `sync` 可用

## 第二次 --apply 也失败：dd 读到 0 字节（根因是并发 adb）

- 现象：`lba 0: 0 bytes (0 B) copied` / `lba 124186591: 0 bytes (0 B) copied`，
  然后 `sector 1 differs: got 4546492050415254000001005c… want 4546492050415254000001005c…`
  —— got/want 的**前 16 字节完全相同**（`EFI PART` + revision 0x00010000 + header_size 0x5c），
  只有偏移 16 的 header CRC 不同，即"旧 header vs 新 header" → **写入根本没发生**
- **附带结论：那次的"回滚"同样是 0 字节写入，实际什么都没写；设备内容从头到尾没变**
  （所以两次失败后 sha256 都还是 `dc368597…`）
- 排除项（都实测过）：
  - `adb push` 16 B / 139,264 B 都正常，设备端大小正确
  - 直接调用脚本的 `write_sectors`（`DEVICE` monkey-patch 成 `/dev/null`）→
    `139264 bytes (136 K) copied`，两次都正常
  - `/dev/block/sda` = `brw------- root root`，root 可写
  - toybox dd 支持 `conv=notrunc,fsync`；`sync` 可用
- **根因：并发 adb**。recovery 的 adbd 在被另一个 adb 会话打断时，
  `adb push` 仍返回 0，但只留下一个**空文件**；dd 于是老实报 0 字节。
  用户跑脚本时我这边正在跑 push 测试（`pushtest.txt` / `big.bin` 时间戳同为 09:40）
- 修复（commit e32f0af）：push 后 `stat -c%s` 核对设备端落地字节数，不符立即报错

## 真凶：baseband_guard（用户自加的 LSM，安卓内核）

- 第四次 `--apply` 终于露出真实报错：
  `dd: /dev/block/sda: write error: Operation not permitted`，
  但 `1+0 records in` —— **stdin 传输是好的，是内核拒绝写入**
- `dmesg` 给出答案：
  `baseband_guard: deny write to protected partition dev=8:0 path=/dev/block/sda`
- 初始化行：`LSM: initializing lsm=capability,safesetid,selinux,bpf,baseband_guard,integrity`
  + `baseband_guard repo: https://github.com/vc-teahouse/Baseband-guard`
  + `version: 028ff7fd`
- **这是用户自己往安卓内核里加的 LSM，不是 XNU 内核**（recovery 跑的是安卓内核）
- 它按 **SELinux domain** 判 trusted：`baseband_guard: pid 694 has been marked as
  untrusted process due to its selinux domain`，`su` 域是 untrusted → 整盘 sda 拒写
- 不可卸载：没有 `/sys/module/baseband_guard`（built-in），`rmmod` 报 No such file
- `/sys/block/sda/ro` = 0、`blockdev --setrw` 也能跑，但写入仍 EPERM —— 保护在 LSM 层，
  不在 bd_read_only 层。**用 `/dev/null` 当输入写 0 字节那次 exit=0 是假象**：

## 为什么"只刷 boot"对 XNU 是成立的（20:14 回答用户）

用户质疑：这台是 GKI 2.0 布局，boot 通常只放 Linux kernel，ramdisk 在 init_boot，
只刷 boot 会不会有问题。**不会**，三条理由：

1. **XNU 的 boot.img 是自包含的**：`ramdisk_size = 0`，payload（167,772,160 B，
   含 XNU + 驱动 + ram-data 种子）嵌在 **kernel 字段**里
   （`kernel = gzip(shim 112 + FD 0x300000 + payload) + DTB 1,431,340`）。
   它不依赖任何外部 ramdisk。
2. **init_boot 完全不碰**：`fastboot flash boot` 只写 boot 分区。安卓的 generic
   ramdisk 原样留在 init_boot 里，bootloader 仍会把它加载进内存，但 XNU 的
   BootShim/UEFI 不读那块内存 —— 它从内嵌 payload 里的 Data 卷启动。
3. **已经实证过**：v221 就是只刷 boot 启动的，能跑到 panic 屏
   （`UFS ROOT FAILURE / stage=GPT entries`），说明高通 bootloader 接受
   「header v4 + 空 ramdisk」的 boot.img，不会因为 init_boot 里有 ramdisk 而拒绝。

补充：vendor_boot 的 dtb 也不冲突 —— v222 自己带了 DTB（尾部 `d00dfeed`，1,431,340 B），
header v4 的 dtb 字段优先。

**回安卓只需刷回原厂 boot**（`out/backup/boot_a.img`），init_boot / vendor_boot 从未被修改。
