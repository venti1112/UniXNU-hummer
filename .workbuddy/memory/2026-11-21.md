## v220 panic 定位：SMMU 规划把「我们自己的残留映射」当成冲突

### panic 屏逐字段解码（用户手工 OCR，红绿蓝三条线在顶部）
- `UFS ROOT FAILURE: conflicting UFS stream mapping`、`stage=SMMU planning result=e00002d8`
  （`e00002d8` = `kIOReturnNotReady`）
- `SMMU smr=80000060 s2cr=00000001 cbar=00000000 sctlr=00000000`
- `SMMU slot=1 id1=60000053`、`id2=5111`、`cba2r=0`
- `@NativeUfs.cpp:1340`

### 解码
- `id1=0x60000053` → `banks = 0x53 = 83`、`pages = 1<<(((id1>>28)&7)+1) = 128`
  → 最高 bank = 82，`(128+83)*4096 = 0xd3000`，必须靠 SM8750 的 `kUfsSmmuMapBytes=0x100000`
  才过几何检查（默认 `0xd0000` 会判 "unsupported SMMU geometry"）。这条反过来证明 id1 读数可信。
- `smr=0x80000060` → VALID + stream 0x60、mask=0；`s2cr=0x1` → TYPE=0、CBNDX=**1**。
- 规划器从 bank 82 往下找，`ourBank` 要求 `s2cr&255 == p.bank`，永远不等于 1
  → `usable=false` → `conflicting UFS stream mapping`，`slot=1` 与屏幕完全一致。
- **注意**：失败路径不写 `gRootDiagnostic.cbar/sctlr`，屏上那两个 0 是默认值，不是硬件读数。
  据此不能推断 bank 1 未被配置（PKX110 的 run-15 探针里对应的 bank 0 是 `SCTLR.M=1` + `CBAR=0x12345000`）。

### 根因
`SmmuTakeover.h: planUfsSmmuBank` 只允许两种「我们自己的条目」：已经落在我们选的 bank 上（reuse），
或者 `NATIVE_UFS_SM8750` 特判的 `s2cr == 0`（PKX110 固件把 SID 0x60 留在 bank 0）。
hummer 固件把 SID 0x60 留在 **bank 1**，`s2cr=1` 不在特判里 → 直接 panic。
上游注释只考虑了反方向（别的 stream 占了我的 bank），没考虑「我的 stream 已被映射到别的 bank」。

### 修法（`patches/native-ufs-sm8750.patch`，改 `SmmuTakeover.h` + `tests/SmmuTakeover.cpp`）
- 精确匹配（`mask == 0` 且只有一条）时，**不管它指向哪个 bank 都归我们处置**：
  `p.reuse = ourBank`，落在别处就由 `configureUfsSmmu` 把 S2CR/SMR 改写到选定 bank。
- 只有通配（`mask != 0`）或同一 stream 的第二条条目才算 `conflicting UFS stream mapping`。
- `retryable` 去掉 "conflicting"（它已与 bank 无关，重试 8 次纯浪费）。
- 保留「复用 bank 的 CBA2R/CBAR 不符预期就不修复」的守卫：不再原地修，而是下移一个 bank；
  测试里把下方 bank 全部占住以保持「拒绝时不写硬件」这条性质仍被覆盖。

默认几何与 SM8750 几何都 PASS；g++/clang++ × ASan+UBSan 全绿。
新增用例直接复刻 v220 现场（`idr0=0x4c017e84`、`idr1=0x60000053`、`SMR[1]=0x80000060`、
`S2CR[1]=1`、`DMA=0x8cddeb00`），断言 `bank=82 slot=1 reuse=false`、写 5 个寄存器、
第二次规划 `reuse=true`，且 bank 1 的 CBAR/SCTLR 原封不动。

### 工程经验
- `.cache/prepare-sxp5oyu1/tree` 是**中断留下的半成品**（补丁未打），别拿它当构建源码看；
  真正编进内核的是 `.cache/upstream-<rev>-<指纹>/`（目录本身就是树，没有 `tree/` 子层）。
- 补丁按文件分节，每节的 hunk 都相对**原始文件**；要改已经打过补丁的内容，得重新生成
  「原始 → 最终」的整节 diff，而不是在原 hunk 上叠加。
- 拼节脚本注意 `diff -u` 的头两行（`--- a/` / `+++ b/`）要整对替换，只切一行会留下重复的 `+++`。
