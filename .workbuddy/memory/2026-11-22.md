# 2026-11-22

## v223 上机：系统能启动并操作了，但 2 秒一帧

用户反馈：「可以启动并操作了，但是卡的要命，目测 2 秒一帧」。

**这是第一次真正可交互**：系统进锁屏、触屏能用（Synaptics S3910 驱动工作），
之前关掉 `qcom-usb-debug=1` 后不再被 USB worker 带走。

**性能瓶颈（按影响排序）**：

1. **GPU 完全没参与渲染** —— README 明确写着「SpringBoard 目前是纯 CPU 合成」，
   状态表里 GPU 是「⬜ 只有 `HummerAdrenoProbe.c` 探针」。
   `patches/adreno-a830.patch`（2203 行）确实搬来了 A830 的 `NativeAdrenoGpu::start()`、
   GMU/CP/ring/user client，但 `package/` 里只有：
   - `HummerAdrenoProbe.c` — `native_adreno_firmware_probe()`，GMU TCM 写测试，
     `hummer-adreno-probe=1` 才跑，结果塞进 panic 文本
   - `HummerAdrenoBringup.cpp` — `hummer_adreno_bringup_probe()`
   也就是说只到 bringup 阶段，**没有接 Metal / IOGraphics**，SpringBoard 的图层合成
   （1264×2780 ≈ 350 万像素/帧）全压在 CPU 上 → 0.5 fps 是这个架构的必然结果。
2. **只用 6 核** —— README「后续」第 4 项：两个 Oryon prime 在 MPIDR **Affinity2**，
   而 XNU 拓扑只用 Aff1/0，`MAX_CPU_CLUSTERS` 又被 6 核占满。要一起改
   XNU 拓扑映射、`start.s` 的 MPIDR 掩码、ArmCpu 的 PSCI 亲和性掩码、ADT 生成器。
3. **CPU 调频未知** —— 没找到 cpufreq/OPP 代码，`package/HummerPlatformPower.cpp`
   只 hook 了 PMGR（`sheng_pmgr_run`），不确定核是否跑在最高频。

**改进路径（性价比从高到低）**：8 核 → CPU 调频 → GPU。
GPU 是最大提升但工程量最大（要接 Metal 服务 + IOGraphics 完整栈）。

## 找到性能根因：GPU 驱动齐全但开关从未打开（11:38）

用户问「有没有已有可用 A830 驱动」。答案：**有，而且是完整的**。

**驱动侧**：`drivers/NativeAdreno`（submodule，`https://github.com/UniXNU/NativeAdreno.git`）
里 A830 全套都在 —— `NativeAdrenoA830HwInit.cpp/.h`、`A830Regs.h`、ring/CP、IRQ、
Gen8 protection、UBWC、restore state、ZAP 认证、VM、user client、publish。
README 原文：13T 已验到 **Metal registration + submissions/completions 1039/1039 +
presentation 518/0**（"controlled shader correctness, measured performance and
long-duration stability remain unqualified"）。

**板级接入侧**：`package/HummerGpu.cpp`（26 KB，v185 起取代 `HummerAdrenoBringup.cpp`），
覆盖 GPUCC 上电、SMMU 路由、GMU cold start + HFI、CP、ZAP、ring、publish、Metal。
`scripts/build-hummer-adreno-kits.py` 的 `DRIVER_SOURCES` 会把它和
`Sm8750Gmu*.c`/`Sm8750Gpu{Power,Smmu,Zap}.c`/`HummerGpuVotes.c` 一起编进 kit，
CI 的 archive 19/20 确实跑过且没报错。

**真正的原因（一行）**：

```c
extern "C" int hummer_gpu_start() {
    if(g.attempted) return kIOReturnBusy;
    uint32_t enabled=0;
    if(!PE_parse_boot_argn("hummer-adreno-bringup",&enabled,sizeof(enabled)) || !enabled)
        return kIOReturnUnsupported;      // ← 默认在这里就返回了
```

`board.toml` 的 `kernel_args` 里**从来没有 `hummer-adreno-bringup`**，所以 GPU 路径
每次开机第一行就退出，SpringBoard 只能纯 CPU 合成 → 1264x2780 每帧 350 万像素，
2 秒一帧合理。

**安全性确认**：`HummerGpu.cpp` 和整个 `drivers/NativeAdreno` 里 `panic(` 出现 0 次；
失败路径只有 `boot_progress_display_status()` + `IOLog("hummer GPU stopped at %s: %d")`
+ 返回 rc。所以开启后即使 ZAP/GMU 挂掉也不会重启，只是回到 CPU 合成。

**动作（commit 013be38）**：`kernel_args` 加 `"hummer-adreno-bringup=1"`，
触发 CI **run 44981598284**。之后下载 payload → 打包 v224 → 刷 boot。
`scripts/stage7/Stage7Probe.cpp:138` 是唯一调用 `hummer_gpu_start()` 的地方。

## 开了 GPU 还是卡：查到的三处缺口（12:13）

用户：「没有任何报错，但是还是很卡，感觉 CPU 跑在低频」。

**1. CPU 频率完全没人管（确认）**
`package/` 里搜 `freq|OPP|dvfs|cpufreq|performance_state`，命中的只有 GPU 侧
（`HummerGpuVotes.c` 的 525 MHz、`Sm8750Gmu.c` 的 `Sm8750GmuSetPerformance`）。
**没有任何 CPU 调频代码**；`scripts/make-hummer-adt.py` 的 cpu%d 节点只写
`state` 和 `timebase-frequency`，**没有 `clock-frequency` / `voltage-states`**。
`package/HummerPlatformPower.cpp` 的 `sheng_pmgr_run()` 只是加载 ApplePMGR kext
再建 HummerPlatformPower/ApplePMGRNub，没有频率表可喂。所以 CPU 跑在 ABL 交接时的
固定频率上，XNU 既不读也不改。

**2. 显示路径的 GPU hand-off 是个 stub（关键）**
`package/NativeLegacyDisplay.cpp:297` 每帧调用
`native_legacy_gpu_offer(this, memory, sourceStride, width, height)`，
但唯一的定义在 `scripts/stage7/Stage7Probe.cpp:81`：
`bool native_legacy_gpu_offer(...) { return false; }` —— **永远 false**，
于是每帧都落到 CPU `memcpy`。注释里写的 `sheng-fb-gpu=1` 这个 boot-arg
在整个 package/scripts 里**没有任何 PE_parse_boot_argn 读取它**，功能没实现。

**3. accelerator 是给 Metal 发现用的，不是给 WindowServer 合成用的**
`drivers/NativeAdreno/NativeAdrenoAccelerator.cpp` 里是 `AGXAccelerator`，
注释写明「registry-visible accelerator for the original Metal discovery
(IOServiceMatching("IOAcceleratorES"))」；`HummerGpu.cpp:376-385` 只有在
`native_adreno_accelerator_{allocate,instance_size,static_init}` 都存在且
instance_size==136 时才加载它。所以即便 Metal 注册成功，SpringBoard 的图层合成
是否真的落到 GPU，仍取决于 WindowServer 是否走 IOGraphics/IOAccel 那条路。

**下一步诊断点**：`scripts/stage7/Stage7Probe.cpp:138` 的
`progress("GPU start", (uint32_t)hummer_gpu_start())` 会把返回码画在屏幕上 ——
0 表示 GPUCC→SMMU→GMU→CP→ZAP→ring→publish→Metal 整条走通；非 0 就停在某个 stage。
重启时盯这一行，比盲猜快。

## CPU 调频移植：SCMI performance 协议（13:00）

按用户要求「先把 CPU 频率补上」。查证过程与结论：

**纠正一个我自己的误判**：`hummer-adreno-bringup=1` 从 v185 起就一直在
`board.toml` 的 kernel_args 里（第 288 行），上一轮我又加了一份，还写
「GPU 从未启动过」——错的。**0.5 → 1.5 帧的提升来自关掉 `qcom-usb-debug`**
（USB worker 每 5 ms 轮询、60 秒超时 panic），与 GPU 无关。重复段已删除。

**真正的参考项目**：`iola1999/hackios-redmi-k90-annibale`（REDMI K90，
同 SM8750「sun」的 XNU 移植，已做到 52–56 fps）。已 clone 到
`/home/venti1112/project/hackios-annibale-ref`（用户要求不放 /tmp）。

**关键发现**：
- 他们的 CPU 调频是 `hackios-xnu-kernel/xnu/files/bsd/dev/annibale/annibale_cpufreq.c`
  （944 行），**机制是 SCMI performance 协议 0x13**，不是直接写 EPSS：
  CPUCP 固件管时钟电压，OS 通过共享内存 + 邮箱门铃申请档位。
- 硬件参数与 hummer **完全一致**（hummer DTB 里确认）：
  `mmio-sram@0x17b4e000`（0x400）、`scmi-shmem@0`（0x200）、
  `qcom,cpucp@0x17830000`（0x300）、doorbell `0x100+4`。
- 双域：domain 0 = cluster 0 六核，domain 1 = cluster 1 两核；
  **ABL 交接时 domain 1 停在最慢的 1017.6 MHz**。
- 他们的流畅（52–56 fps）来自**完整 Metal 用户态**（Mesa/freedreno +
  `annibalemetal.m` + AIR 编译器），hummer 仓库里**完全没有这一层** ——
  这才是 2 秒一帧的真正原因，CPU 调频只能改善一部分。

## 原厂固件到手：hummer 的地址与 K90 完全不同（12:40）

用户提供原厂固件解包：`/run/media/venti1112/系统/Users/37883/Downloads/extracted_20261114_173210/`
（54 个 img，含 boot/vendor_boot/dtbo/cpucp/cpucp_dtb/abl/super 等）。
`vendor_boot.img` 头部 v4、page 4096、vendor_ramdisk 18,480,692、**dtb 6,821,771**，
提取到 `/tmp/hummer-vendor.dtb` 后反编译。

**关键结论：不能照搬 K90 的地址。**

| 项 | K90（annibale） | **hummer（本机 DTB）** |
|---|---|---|
| SCMI shmem | `0x17b4e000` (0x200) | **`0x17d09400`** (0x400) |
| CPUCP rx | — | **`0x17d90000`** (0x2000) |
| CPUCP tx | `0x17830000` | **`0x17400000`** (0x10) |
| 调频节点 | SCMI 0x13 | **`qcom,cpufreq-epss` 三个域** |

hummer 的 EPSS：

```
cpufreq_hw: qcom,cpufreq-hw {
    compatible = "qcom,cpufreq-epss";
    reg = <0x17d91000 0x1000 0x17d92000 0x1000 0x17d93000 0x1000>;
    reg-names = "freq-domain0", "freq-domain1", "freq-domain2";
};
```

CPU → 域（`qcom,freq-domain = <0x07 N>`）：
- CPU0–2（cpu@0/100/200）→ domain 0
- CPU3–6（cpu@300/400/500/600）→ domain 1
- CPU7（cpu@700）→ domain 2

即 **3+4+1 三域**，与 K90 的 6+2 不同。

**EPSS 寄存器布局**（Linux `qcom-cpufreq-hw.c` 的 `epss_soc_data`）：
`enable=0x0`（bit0 硬件持有）、`domain_state=0x20`（低 8 位是 LMh 节流档）、
`dcvs_ctrl=0xb0`（bit0 per-core DCVS）、`freq_lut=0x100`（每行 4 B）、
`volt_lut=0x200`、`intr_clr=0x308`、**`perf_state=0x320`（写档位 index 即请求）**。
LUT 行位域：`SRC[31:30]`、`CORE_COUNT[18:16]`（==1 为 turbo，不可请求）、
`VOLT[11:0]`、`L_VAL[7:0]`；`SRC==0` 时 `freq = xo_rate * L_VAL`。

**改写**：删掉 SCMI 版（941 行移植，地址不匹配会写错寄存器），换成
`package/HummerCpufreq.c` —— EPSS 直接写寄存器，约 180 行，无邮箱协议。
先只要 `cpufreq=2`（只读：打印 enable/dcvs/LUT 全表/perf_state），
确认档位表和 XO 频率后再改 `cpufreq=3` 锁最高档。
编译脚本、defconfig、Stage7Probe 挂接点都沿用上一轮的，不用改。
